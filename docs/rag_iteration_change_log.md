# RAG 迭代记录与修改要点

本文档用于面试展示和后续复盘，记录每次迭代的目标、修改内容、验证结果和剩余问题。原则：运行逻辑不写“问题到答案”的映射，评估集只用于验证，不进入回答规则；只有验证有效的迭代才写入本文档。

## 当前测试规模

- 自然语言场景集：29 个场景，其中 24 个单轮问题、5 条多轮链路，共 20 轮多轮问答。
- 聚焦单轮测试集：72 个问题，其中 68 个计入检索评分，4 个为边界/拒答类。
- 多轮专项测试：4 条链路，共 15 轮。

## 当前核心指标

- 自然语言场景集：Hit@1 = 1.000，Hit@3 = 1.000，Hit@5 = 1.000。
- 自然语言场景集：数值/关键字段召回 = 0.958。
- 聚焦单轮测试集：Hit@1 = 0.971，Hit@3 = 1.000，Hit@5 = 1.000。
- 聚焦单轮测试集：数值/关键字段召回 = 0.778。
- 多轮专项测试：检索 Hit@5 = 1.000，行为断言命中率 = 1.000。
- 聚焦单轮测试集：剩余 Top1 未命中主要来自现行通用规范与旧版设计规范的排序口径冲突。

## 迭代 1：多规范知识库与基础检索

目标：从单一规范文本扩展为多规范知识库，支持建筑防火通用规范、消防设施通用规范、建筑设计防火规范、汽车库专项规范的联合检索。

修改要点：

- 建立 `data/raw_pdfs`、`data/processed_text`、`data/vectorstore`、`data/policy` 等目录。
- 解析 PDF 页面、条文号、页码和原文片段，生成 `chunks.jsonl`。
- 建立 FAISS 向量库和 BM25 关键词索引。
- 增加规范注册表和新旧规范关联提醒。

验证结果：

- 可以按标准号、条文号、页码返回引用来源。
- 能同时召回通用规范、专项规范和旧版设计规范候选。

剩余问题：

- PDF 表格和跨页条文仍可能切断关键字段。
- 旧规范与现行通用规范之间的优先级需要产品策略解释。

## 迭代 2：混合召回与本地重排

目标：提升 Top-K 召回稳定性，减少只靠向量检索导致的条文号、数值和关键词丢失。

修改要点：

- 使用 BM25 + FAISS 混合召回。
- BM25 负责条文号、标准号、数值、专有名词的精确召回。
- FAISS 负责自然语言语义相近问题的补充召回。
- 增加本地 rerank，考虑条文号、页码、问题字段、旧规范风险和候选分差。

验证结果：

- Top5 召回稳定性明显提升。
- 多数自然语言问题的正确条文可以进入 Top5。

剩余问题：

- 本地 rerank 仍包含领域规则，长期应替换或补充为可评估的语义 reranker。
- 部分相邻条文仍会竞争 Top1。

## 迭代 3：检索可视化与证据链展示

目标：让用户知道答案从哪里来，避免 RAG 黑箱。

修改要点：

- 在回答下方折叠展示引用来源。
- 展示来源文件、标准号、条文号、PDF 物理页和原文片段。
- Expert Mode 展示 hybrid score、BM25 score、vector score、chunk id、rerank notes。
- 页面默认保留简洁答案，复杂检索细节默认折叠。

验证结果：

- 面试中可以解释“为什么这个答案不是模型编造”。
- 用户可以点开原文片段进行人工核查。

剩余问题：

- 原文片段仍然偏长，需要继续优化摘要和高亮。
- 字段抽取层还不够稳定，不能总是精准抽出数值、条件和适用场景。

## 迭代 4：自然语言测试集与边界拒答

目标：从肉眼观察转为可量化评估。

修改要点：

- 增加自然语言场景集，覆盖简单事实、判断题、边界问题和多轮链路。
- 增加聚焦单轮测试集，覆盖更多消防规范条款。
- 增加边界拒答类问题，例如地方审查口径、版本差异、缺少项目条件等。
- 输出 JSON 和 Markdown 评估报告。

验证结果：

- 自然语言场景集当前 Hit@1 = 1.000。
- 聚焦单轮测试集当前 Hit@1 = 0.971。
- 边界拒答通过率为 1.000。

剩余问题：

- 测试集规模仍偏小。
- Gold label 需要区分“严格原条文命中”和“等效现行条文命中”。

## 迭代 5：数值判断和字段召回优化

目标：解决“设计值是否合规”类问题召回不稳定的问题。

修改要点：

- 对“多少/不应小于/不应大于”等数值型问题，提高含明确数值和相同对象字段的候选排序。
- 对“0.78m 可以吗”“58m 能不能接受”等判断题，识别问题中给出的设计值，并优先召回对应规范限值。
- 对“只设一个/设置一个”等中文数量表达进行归一化，减少阿拉伯数字和中文数字不一致带来的召回损失。
- 增加条文开头主语匹配权重，优先选择适用对象更明确的条文。

验证结果：

- 自然语言场景集数值/关键字段召回从 0.708 提升到 0.833。
- 自然语言场景集 Hit@1 提升到 1.000。
- 聚焦单轮测试集 Hit@1 提升到 0.971，Hit@5 保持 1.000。

剩余问题：

- 聚焦单轮测试集的数值/关键字段召回仍只有 0.431。
- 需要独立字段抽取层，而不是只依赖候选文本和 LLM 总结。

## 迭代 6：多轮问答展示与短答优先

目标：保留 v1 的直接回答体验，同时保留 v2 的证据可靠性。

修改要点：

- DeepSeek 回答时区分“用户本轮问题”和“检索补全文”。
- 追问时要求优先回答本轮差异点，不重复上一轮完整规则。
- 页面不直接暴露内部拼接后的检索问题，只显示简洁的上下文提示。
- Expert Mode 中保留上下文触发原因和检索补全文，便于审查。

验证结果：

- 多轮评估中上下文行为命中率保持 1.000。
- 回答更接近连续问答，而不是每轮生成一篇完整报告。

剩余问题：

- 当前上下文判断仍以规则为主，不够像真实 LLM 对话。
- 下一步应引入 Context Router，先判断新问题/追问/证据追问/纠错/对比，再检索。

## 迭代 7：置信度解释与保守显示

目标：解释“证据置信度中”和“模型判断置信度中”从何而来，避免用户误以为模型在黑箱打分。

修改要点：

- 页面新增“置信度判定依据”折叠面板。
- 证据置信度展示本地判定依据：字段完整性、Top1/Top2 分差、是否旧规范、是否缺页码/条文号/数值字段。
- DeepSeek 模型置信度新增 `confidence_reason` 字段，要求模型说明为什么给出 high / medium / low。
- 如果模型原始置信度高于证据置信度，页面按证据等级保守显示，并说明“原始等级”和“保守显示原因”。

验证结果：

- 用户可以看到“中”是因为字段缺失、候选分差小、旧规范风险或模型认为适用条件不足。
- 模型判断不再和证据置信度直接冲突。

剩余问题：

- 置信度仍是启发式评分，不是统计校准概率。
- 后续需要用更多人工标注样本校准 high / medium / low 与真实正确率之间的关系。

## 迭代 8：LLM 上下文路由与新话题切换

目标：修复多轮对话中“新问题被错误接到上一轮上下文”的问题，尤其是从汽车库疏散距离切换到疏散出口门净宽时不应继承旧证据。

修改要点：

- 新增 `scripts/context_router.py`，用 DeepSeek 只判断上下文关系，不回答规范问题。
- 路由输出 `new_topic / follow_up / evidence_request / comparison / correction`、是否继承上下文、检索改写问题和判定原因。
- App 查询流程先调用上下文路由；如果判定为新话题，则不合并上一轮证据。
- API 不可用时才使用保守规则兜底。
- Expert Mode 中展示上下文判断来源、模式、原因和检索补全文。

验证结果：

- “那如果是医疗建筑呢？”判定为追问，继承上一轮“高层公共建筑疏散楼梯净宽”上下文。
- “这两个数值为什么不一样？”判定为追问，继承前两轮数值比较上下文。
- “我有一个地下汽车库，设置了自动灭火系统，室内最远点到人员安全出口大概 58 米，这个距离能不能接受？”判定为新话题，不继承前面的楼梯净宽上下文。
- “建筑里疏散出口门净宽 0.78 米，但人流很少，这样可以吗？”判定为新话题，不继承上一轮地下汽车库疏散距离证据。

剩余问题：

- 上下文路由依赖 DeepSeek API，网络失败时仍会回到规则兜底。
- 多轮评估脚本后续应同步使用 Context Router，否则离线评估与真实 App 流程不完全一致。
- 仍需扩大多轮测试集，覆盖更多主题切换和纠错场景。

## 迭代 9：评估流程同步与字段召回优化

目标：让离线评估流程与真实 App 查询流程一致，并提升“数值/关键字段”召回指标，避免只看标准号和条文号命中。

修改要点：

- 新增 `scripts/field_extraction.py`，统一抽取数值、单位、适用等级、类型、条件词和规范要求词。
- App 与评估脚本共用同一套字段召回判断，减少页面展示和离线评估口径不一致。
- `evaluate_natural_scenarios.py` 与 `evaluate_multiturn_tests.py` 同步使用 Context Router，不再只靠规则判断追问。
- 多轮评估结果记录 Context Router 的模式分布、来源分布和承接上下文轮数。
- 页面中的“置信度判定依据”和“检索依据风险与复核提示”默认折叠，并压低折叠区字体，避免干扰正文答案。

验证结果：

- 编译检查通过：`field_extraction.py`、`context_router.py`、`conversation_context.py`、两个评估脚本和 `retrieval_app.py` 均无语法错误。
- 聚焦单轮测试集：72 题，68 题计入评分，Hit@1 = 0.971，Hit@5 = 1.000，数值/关键字段召回 = 0.778。
- 自然语言场景集：29 个场景，Hit@1 = 1.000，边界拒答通过率 = 1.000，数值/关键字段召回 = 0.958。
- 自然语言多轮：5 条链路、20 轮，Context Router 全部由 LLM 判断，其中 15 轮判定为承接上下文，可回答率 = 1.000。
- 多轮专项测试：4 条链路、15 轮，检索 Hit@5 = 1.000，行为断言命中率 = 1.000。

剩余问题：

- 当前评估集规模仍偏小，尤其多轮只有 9 条链路、35 轮左右，还不足以证明复杂真实审查场景稳定。
- 字段抽取仍是启发式，不等于完整结构化条文解析；复杂表格、跨页条文和条文说明仍可能漏字段。
- Top1 仍有 2 个聚焦单轮样本未命中，下一步需要做失败样本归因和 reranker A/B，而不是写死问题。

## 迭代 10：IFC 解析入口与 RAG 审查链路

目标：将 BIM/IFC 模型接入现有规范 RAG，但保持职责分离：IFC 负责提取项目事实，RAG 负责召回规范依据，LLM 负责基于证据生成合规判断。

修改要点：

- 新增 `scripts/ifc_fire_parser.py`，使用 IfcOpenShell 解析 IFC 文件。
- 抽取项目、建筑、楼层、空间、门、楼梯、坡道、电梯、消防设施等对象数量。
- 抽取门宽、门高、楼层高程、防火性能、空间面积、外门属性等可审查字段。
- 根据 IFC 类型、属性集和对象命名识别疑似汽车库、中庭、疏散出口、消防设施等场景。
- 新增 IFC 页面入口，支持上传 `.ifc` 文件、展示解析摘要、查看审查字段、自动生成规范审查问题。
- 自动生成的问题仍送入原有 RAG 问答链路，不写问题到答案的映射。
- 新增 `docs/ifc_rag_processing_chain.md`，说明 IFC 解析方法、处理链路和与消防合规检查系统的关系。

验证结果：

- 编译检查通过：`scripts/ifc_fire_parser.py` 与 `app/retrieval_app.py` 均无语法错误。
- 使用 IfcOpenShell 自带 IFC schema 文件做兼容性烟测，解析器可打开 IFC 文件并返回空模型摘要，不崩溃。
- 使用临时构造的 IFC4 样本做字段烟测：成功识别 2 个楼层、1 扇门、建筑高度约 4.2m、门宽 0.78m，并生成“建筑高度复核”和“门净宽复核”两个审查问题。

剩余问题：

- 当前 IFC 解析仍是字段抽取层，不包含真实疏散路径几何计算。
- 门是否真的是疏散门、空间是否真的是汽车库/中庭，目前主要依赖 IFC 类型、属性和命名，需要人工复核。
- 后续需要加入房间-门-楼梯-出口拓扑关系、路径距离计算和 IFC 样例测试集。

## 下一步建议

1. 先用真实 IFC 文件测试字段抽取质量，记录哪些字段能读出、哪些字段缺失。
2. 增加 IFC 字段质量评分：可直接审查、需要人工确认、无法审查。
3. 做门-空间-楼层-楼梯的拓扑关系，进入疏散距离和安全出口数量审查。
4. 对 Top1 未命中样本继续做失败归因和 reranker A/B。

## 迭代 11：IFC 可选入口与纯规范问答解耦

目标：避免用户误以为必须先上传或解析 IFC 才能使用规范 RAG 问答。

修改要点：

- 将 IFC 上传与解析面板改为默认折叠的可选入口。
- 主页面仍保留纯规范问答作为默认工作流，用户可以不上传 IFC 直接提问。
- IFC 解析结果只用于生成项目审查问题，不改变规范问答的独立检索能力。

验证结果：

- 编译检查通过：`app/retrieval_app.py` 与 `scripts/ifc_fire_parser.py` 无语法错误。
- Streamlit 健康检查返回 `ok`。

剩余问题：

- 后续需要在 UI 上进一步区分“规范知识问答”和“项目模型审查”两个工作模式，减少用户误解。

## 迭代 12：IFC 审查问题归一化与页面崩溃修复

目标：修复 IFC 自动生成问题检索跑偏，以及 Streamlit 折叠面板嵌套导致页面崩溃的问题。

修改要点：

- 修复 Streamlit `Expander may not be nested inside other expanders` 错误：IFC 可选入口外层保留折叠，内部不再创建嵌套折叠框。
- IFC 门审查问题不再把 Revit 族名、实例编号、`1250mm x 2010mm` 等噪声直接塞入检索问题。
- 新增 IFC 审查问题归一化：保留门宽、构件类型、是否疑似疏散出口、待人工确认用途等关键信息。
- 对用途未识别的门，检索问题会明确要求按疏散出口门、疏散门、住宅户门等可能场景查最低净宽，并提示必须人工确认门的真实用途。

验证结果：

- 编译检查通过：`app/retrieval_app.py` 与 `scripts/ifc_fire_parser.py` 无语法错误。
- 使用用户反馈中的 IFC 门宽问题做烟测，归一化后的检索 Top1 命中 `GB 55037-2022 第7.1.4条`，PDF 物理页第 38 页。
- Top5 不再被 Revit 族名、实例编号和尺寸字符串牵引到观众厅或构件耐火表。

剩余问题：

- “普通门”本身没有统一最低净宽结论，仍必须人工确认它是否是疏散门、户门、安全出口门或普通房间门。
- IFC 中门的真实消防角色不能只靠名称判断，后续需要结合空间连接关系、门所在边界和出口拓扑判断。

## 迭代 13：规范问答与 IFC 项目审查工作区分离

目标：避免 IFC 解析结果污染连续问答窗口，并去除面向使用者页面里的内部评估指标展示。

修改要点：

- 页面拆分为“规范问答”和“IFC 模型解析”两个工作模式。
- 规范问答模式保持独立，可不上传 IFC 直接提问。
- IFC 模型解析模式只展示模型事实、字段质量、缺失字段和项目审查问题。
- IFC 模块内点击检索后，结果只显示在 IFC 模块内部，不写入连续问答历史。
- 删除侧边栏中的自然语言场景集、Hit@1、Hit@5、迭代记录路径等内部评估信息。
- IFC 解析增加建筑使用功能的低置信识别和字段质量提示，避免把“疑似住宅/公共建筑”当成确定审查条件。
- IFC 生成门宽问题时按楼层、宽度和用途去重，减少同类门重复生成相同问题。

验证结果：

- 编译检查通过：`app/retrieval_app.py` 与 `scripts/ifc_fire_parser.py` 无语法错误。
- IFC 烟测中，重复的 1.25m 门只生成一次门净宽复核问题，0.762m 门单独生成复核问题。
- IFC 烟测中，建筑使用功能显示为“疑似住宅/居住建筑，置信度低”，并列出缺失字段。
- Streamlit 健康检查返回 `ok`。

剩余问题：

- IFC 建筑类型仍需依赖更明确的项目属性、空间用途或人工确认。
- 后续要做空间-门-楼梯拓扑关系，否则不能可靠判断门是否为疏散出口门、疏散距离是否合规。

## 迭代 22：多轮证据追溯按主题定位与自包含问题隔离

目标：修复“回到旧主题并追问上一轮数值/条文依据”时被最近无关主题证据覆盖的问题，同时避免把“分别复核”“为什么做防火分隔”等自包含问题误判为上下文追溯。

## 迭代 29：通用确定性数值合规复核

目标：把面积、距离、净宽、耐火极限等可直接比较的数值判断从 LLM 算术中分离出来，消除“1800 ≤ 2000”被偶发判断为超过的问题，同时不针对具体建筑类型或测试题编写特例。

修改要点：

- 新增通用数值复核模块，仅依赖模型输出的 `actual_value / requirement_value / unit / comparator` 结构执行比较，不内置汽车库、住宅、医疗建筑或具体条文。
- 支持 `lte / lt / gte / gt / eq` 比较方向，并统一换算长度、面积、时间和百分比单位。
- 模型必须补充输出 `numeric_checks`、`decision_basis` 和 `non_numeric_failures`；数值规则可以完整覆盖结论时标记为 `numeric_only`，存在用途、部位或版本条件时标记为 `mixed`。
- 确定性复核发现实际值违反限值时，优先把 `PASS` 纠正为 `FAIL`；数值规则完整且实际值、限值都能在传入检索文本中追溯时，才允许把偶发的算术错误从 `FAIL` 纠正回 `PASS`。
- 实际值、限值或比较方向缺失时，把 `PASS` 降级为 `INSUFFICIENT_INFORMATION`，不会猜测数值。
- 增加结论与 `verdict` 的一致性门控，修正“面积超过限值，但未超过允许值”“4500 ≤ 4000，满足要求”等自相矛盾表述。
- 定向评估 `--ids` 或 `--limit` 时写入独立结果文件，不再覆盖完整合规评估报告。
- 新增 10 个确定性复核单元测试，覆盖最小值、最大值、毫米换算、单位冲突、强制 FAIL、证据可追溯纠错、缺失值降级和结论一致性。

验证结果：

- 确定性数值复核单元测试 10/10 通过。
- 完整合规评估 25/25：Verdict Accuracy 100%，Safety False Negative Rate 0%，运行错误 0。
- 此前不稳定的 COMP_011 连续回归通过，COMP_012、COMP_013 的 PASS/FAIL 方向也保持正确。

剩余问题：

- 数值规则仍依赖 LLM 正确提取实际值和规范限值；下一步应继续增加候选原文中的数值结构抽取校验，并扩充结构化表格字段。

## 迭代 32：生成后事实一致性与引用完整性门控

目标：在检索证据正确进入上下文后，阻止生成模型继续使用无来源项目事实或未引用规范形成确定性结论，并让独立规范问答与 IFC 合规审查共用同一安全门控。

修改要点：

- 新增通用回答一致性模块，扫描结论、依据、置信度说明、复核提示和合规理由中出现的标准号与条文号。
- 回答点名的规范已存在于候选证据但未引用时，自动补齐对应证据编号；点名本次未召回的规范时，回答降级为低置信度并禁止给出可靠结论。
- 检查 `missing_fields` 与结论是否矛盾：模型一边声明某数值条件待确认，一边将其作为已知事实时，自动降为中置信度条件复核。
- 增加不依赖模型自报缺失字段的事实检查：结论使用“因、由于、基于、已知、模型显示、实际”等表达断言数值项目事实，而用户问题或 IFC 上下文未提供该事实时，拦截确定性结论。
- 正常的“若、如果、当……时”条件式规则不触发拦截；用户已明确提供的项目事实也不触发。
- 合规模式发现事实矛盾时，将 PASS/FAIL 降级为 `INSUFFICIENT_INFORMATION`，避免在缺失适用前提时形成项目合规结论。
- 普通问答与合规问答最大输出上限统一为 1200 tokens，解决复杂结构化 JSON 偶发截断；展示仍受短答提示约束。
- 修正 COMP_011 测试前提：预期按二级耐火等级 2000㎡判断时，输入同步明确二级耐火等级，避免评测答案依赖未提供条件。
- 定向评测产生的 `*.ids.*` 报告作为本地临时文件忽略，完整回归报告继续纳入版本管理。

- 完整合规评估 25/25：Verdict Accuracy 100%，Safety False Negative Rate 0%，运行错误 0。

剩余问题：

- 当前无来源事实检测优先覆盖带因果提示的数值断言；无数值、无明显因果词的隐含项目假设仍需扩展结构化事实声明后再校验。
- 门控发现矛盾时采用保守条件式结论，尚未自动重写为完整且自然的多分支答案；后续可增加受证据约束的二次修复生成，并再次执行同一门控。

## 迭代 33：原子结论证据审计与实时评测闭环

目标：把“检索命中”与“最终回答正确”分开评估，逐项检查一段回答中的规范要求、项目事实和计算结果是否各自有证据，同时解决长时间评测没有可见进度、统一报告被子集运行覆盖的问题。

修改要点：

- 回答结构新增 `atomic_claims`，要求模型把可独立核验的规范要求、项目事实和计算结果拆开，并分别绑定本次候选证据编号。
- 新增通用回答质量审计，只校验证据编号、标准号、条文号、数值和单位等确定性锚点；不按建筑类型、具体规范或测试问题编写生产分支。
- 数值审计统一处理 `1.10m` 与 `1.1m`、`m2`、`m²` 与 `㎡` 等等价格式；支持表格表头单位继承，以及 `2000㎡×2.0=4000㎡` 和 `4000㎡（2000㎡×2.0）` 两种可验证表达。
- 独立规范问答发现任一无证据结论时保持严格拒答；IFC 合规模式允许排除无证据的冗余补充结论，但只有已验证的核心结论和确定性数值规则可以继续参与 PASS/FAIL 判断。
- DeepSeek 请求增加最多 3 次的瞬时故障重试，只重试超时、限流、5xx 和连接中断，非瞬时 4xx 直接返回错误。
- 新增独立 RAG 回答级评测，覆盖直接数值、条件分支、对象不明确、地方规范缺失、复合计算和 OCR 表格风险；测试预期只用于评测，不进入问答链路。
- 统一评测报告按 `pending / running / passed / failed / not_run` 实时写入；子集运行保留其他类别最近一次结果和更新时间，不再覆盖成单一类别报告。
- 合规和回答级评测新增逐案例进度文件，实时记录完成数、总数、当前案例、通过数、错误数和更新时间；评测存在失败时返回非零退出码。
- 补齐 COMP_011 的场景前提，明确为普通坡道式、非机械式及非敞开/错层/斜楼板式地下汽车库，避免预期 PASS 隐含未提供的汽车库类型条件。

验证结果：

- 回答质量、生成一致性和确定性合规单元测试 28/28 通过。
- 独立 RAG 回答级评测 8/8：Answer Pass Rate、Required Claim Pass Rate、Quality Audit Pass Rate 均为 100%，运行错误 0。
- 完整合规评测 25/25：Verdict Accuracy 100%，Safety False Negative Rate 0%，运行错误 0。
- IFC 事实评测 20/20；通过 `eval_all.py --only ifc` 验证统一报告保留全部类别最近结果，IFC 摘要不再为空。
- 逐案例进度在完整合规回归中实际观察到 13/25、24/25 和 25/25 连续刷新。

本轮未重跑的基线：

- 80 个聚焦单轮检索问题和 5 条多轮链路本轮未重新执行；统一报告展示的是其已有结果及文件更新时间，不视为本轮新验证。

剩余问题：

- 表 5.5.18 等 OCR 损坏表格尚未完成可靠行列重建；回答级表格案例当前验证的是发现结构风险后拒绝猜测，不代表系统已经能完整复述该表格行。
- 回答级评测只有 8 个案例，多轮回答仍主要评估检索和上下文行为，下一步需要扩展长对话、跨主题回溯和逐结论证据评测。

## 迭代 34：项目画像优先级与动态 IFC 审查入口

目标：解决用户已补充项目条件后，合规链路仍沿用 IFC 低置信度用途推断或上传时旧建议的问题，并避免固定检查项、事实冲突和复核提示导致错误合规结论。

修改要点：

- 新增项目画像层，将用户自然语言条件、IFC 明确事实和 IFC 低置信度推断分开，并采用“用户明确条件覆盖 IFC 推断；同一实体、同一指标的明确数值冲突必须阻断”的通用优先级。
- 项目条件按自然语言分句区分明确条件与带“可能、疑似、待确认”等语气的不确定条件，不按住宅、汽车库或测试题编写业务分支。
- 新增项目条件应用接口，基于当前项目画像动态生成 3 至 6 个建议复核项；多个同类构件聚合为一个复核入口，上传时的备用门复核项不再重复生成多张卡片。
- 合规问答携带当前项目画像；较早建议中的“疑似、未确认”描述不得覆盖用户最新明确条件。直接调用合规接口且未提供画像时，后端自动补建画像。
- 项目画像服务发生网络波动时降级为本地条件分类与字段型备用建议，用户条件仍立即生效，不向页面暴露底层 SSL 错误。
- 冲突识别要求同一 IFC 实体类型、同一对象、同一指标和同一部位，避免把名称相似但实体不同的尺寸误判为冲突。
- 合规结构区分 `blocking_conditions` 与 `advisory_risks`：前者会改变适用条款或最终判定并阻断 PASS/FAIL，后者保留 OCR 和来源质量复核提示但不无条件推翻已验证原子结论。
- DeepSeek 结构化问答和项目画像接口启用 JSON 输出约束，并对限流、5xx 和连接中断进行有限重试。
- React 工作台新增紧凑的“应用项目条件”状态、已确认条件、模型事实和待补充信息；建议区随画像更新，保持原有页面结构和样式。

验证结果：

- 后端单元测试 41/41 通过，覆盖自然语言条件分类、用户条件优先级、事实冲突阻断、非阻断复核风险和实体错配保护。
- 合规评测 25/25：Verdict Accuracy 100%，Safety False Negative Rate 0，运行错误 0。
- 前端生产构建通过，Sites 页面测试 4/4 通过。
- 使用 Duplex IFC 和“多层住宅”实测：页面显示为已确认项目条件，旧的低置信度住宅推断不再作为建筑用途缺失项；动态建议不再重复生成多张门净宽卡片。

剩余问题：

- 动态项目画像依赖一次额外模型调用；React 会缓存已应用画像，但绕过前端直接调用且未传画像时会增加延迟，后续需增加服务端缓存与耗时统计。
- 建议复核项仍是审查入口，不是完整审查清单；下一步应把宽泛建议拆成可追踪的原子审查任务，并记录事实、适用条款、结论、缺失条件和复核状态。
- 旧会话中已生成的回答会保留原始文本；后续需要标记“基于旧项目条件”的历史结论，避免项目条件更新后被误当作当前结果。

## 迭代 40：IFC 文件清理、会话保存提示与版本兜底细化

目标：修复自检发现的几个可交付风险：IFC 上传文件只增不删、前端本地会话保存失败无提示、版本对比检索兜底把多条条文混在同一个标准下、版本元数据写死。

修改要点：

- 新增多轮场景 `MTF`：用户在中途插入单轮问题后再回到原主题，覆盖“切走再切回”的上下文切换。

验证结果：

- 前端生产构建通过，Sites 页面测试 4/4 通过。

剩余问题：

- 检索兜底候选数量仍可能偏多，后续应按主题相关性做再排序并限制展示条数。
- 多轮“上下文正确但最终答案不直接”的检索组合策略尚未完全解决，仍需要让基准条文和调整条文成对进入生成上下文。

## 迭代 41：BIM 审查企业级体验修正

目标：修正 BIM 审查产品化使用中的直接不适：新 IFC 不清空旧项目条件、摘要单位挤压、解析字段缺少单位校验和空间关系、无法导出基于真实对话的审查报告。

修改要点：

- 上传新 IFC 后自动清空项目条件补充、项目画像和旧审查建议，避免上一个模型的条件被误用到新模型。
- 模型摘要的数值单位改为紧跟在数值后的 `em` 标签，不再单独占一行挤压“推算高度”。
- IFC 解析新增 `unit_quality`：统一声明长度 m、面积 ㎡、高程 m，并标记非正数门宽/窗宽、异常面积和疑似非米高程。
- “解析字段”新增“模型空间关系”树，按 IFC 中的楼层、空间、门、窗、楼梯和未归属对象展示，完全由解析数据生成，不预设建筑类型。
- 消防合规审查页新增“导出报告”，报告内容基于当前模型的解析摘要、项目条件、模型事实问答和真实消防合规问答生成，不使用固定默认结论。

验证结果：

- 后端单元测试 49/49 通过，新增 IFC 单位质量校验测试。
- 前端生产构建通过，Sites 页面测试 4/4 通过。
- 浏览器实测上传新 IFC 后，项目条件从“多层住宅”重置为空。
- 浏览器实测“解析字段”出现 5 个空间关系节点，门、窗、楼梯可按楼层查看；消防合规审查页出现“导出报告”按钮。

剩余问题：

- 批量解析仍按产品方案处理，建议采用“项目内模型列表 + 当前模型切换 + 解析队列”而不是多窗口。
- 模型空间关系当前采用树形展示，后续若需要图形化拓扑，应基于 IFC 真实空间包含关系生成通用图谱，不能按建筑类型硬编码节点。

## 迭代 42：IFC 项目单位换算与高度边界审查

目标：修复 `Myran.ifc` 这类毫米单位模型被直接当成米读取，导致 3 层住宅显示成 6230m 的问题。

修改要点：

- 解析器读取 `IfcProject.UnitsInContext` 的长度单位，支持米、毫米、厘米、分米、千米等 SI 前缀，并按单位系数把楼层高程、门宽、窗宽统一换算为米，空间面积换算为 ㎡。
- 解析结果新增 `project_units`，记录 IFC 原始长度单位、长度换算系数和面积换算系数，前端展示“IFC 原始单位：mm，已换算”。
- `unit_quality` 增加边界审查：建筑高度大于 500m、单层高度大于 15m、门宽/窗宽非正数、空间面积异常时标记为疑似单位或建模异常，要求人工确认；不硬编码“住宅不能超过多少米”来替换结果。
- 当模型空间数量为 0 时，解析限制说明会提示“可能未定义 IfcSpace 或空间与楼层关联缺失”，避免把“解析不到”误当作“模型没有空间”。

验证结果：

- 后端单元测试 50/50 通过，新增毫米单位读取测试。
- 前端生产构建通过。
- 回归解析 Duplex IFC：项目单位为 m，建筑高度仍为 7.25m，门宽仍为 1.25m，未发生误换算。
- 单元测试覆盖 `MILLI` 单位返回 0.001 长度系数和 0.000001 面积系数。

剩余问题：

- 当前支持常见 SI 单位，`IfcConversionBasedUnit` 等自定义单位仍未覆盖，后续需要补通用单位映射。
- 边界审查只提示不自动改值，后续应结合 IFC 单位信息和原始高程同时展示，便于人工核验。

## 迭代 43：空间为 0 改为中性状态

目标：纠正迭代 42 中对“空间为 0”的过度解释。部分 IFC 文件本身就不定义 `IfcSpace`，这属于正常建模差异，不应被当作解析缺失或异常。

修改要点：

- 新增 `space_status` 字段：有空间时返回 `parsed`，无空间时返回 `not_defined`，不再写入解析限制告警。
- `not_defined` 的说明固定为“该模型未定义 IfcSpace；这是部分 IFC 的常见情况，不影响门、窗、楼梯等构件解析。”
- 模型概览在空间为 0 时显示中性说明，不显示红色缺失标签。

评测方法：

- 单元测试：`_space_status([])` 必须返回 `not_defined` 且包含“不影响门、窗、楼梯”；`_space_status([...])` 必须返回 `parsed` 且 count 正确。
- API 集成：上传无 `IfcSpace` 的 IFC，响应中 `space_status.status` 应为 `not_defined`，且 `parser_limits` 不再包含 IfcSpace 告警；上传 Duplex IFC，`space_status.status` 应为 `parsed`。
- UI 回归：模型概览出现“空间状态”中性说明；有空间模型不出现该提示，原有空间关系树仍正常。
- 全量回归：单元测试、前端构建、Sites 测试必须通过。

验证结果：

- 后端单元测试 52/52 通过。
- 前端生产构建通过，Sites 测试 4/4 通过。
- Duplex IFC 实测：`space_status={"status":"parsed","count":21,"note":"已解析 21 个空间。"}`，`parser_limits` 无 IfcSpace 告警。

## 迭代 44：P1 四项能力落地

目标：完成批量解析队列、报告正式化、建筑类型 metadata 过滤、版本日期适用四项 P1 能力，并保持各自可独立评测。

修改要点：

- 批量解析队列：模型来源支持多选 IFC，前端按文件顺序逐批解析并显示进度；会话内保存已解析模型列表，可切换当前模型，每个模型独立保存项目条件、模型问答和审查记录。
- 报告正式化：导出报告升级为结构化 Markdown，包含报告编号、报告状态、模型快照、项目单位、项目日期、结论汇总、逐条问答、引用来源和免责声明；新增 JSON 审查档案导出。
- 建筑类型 metadata 过滤：检索重排增加通用建筑类型识别，住宅、医疗、汽车库、商业、厂房、仓库等场景命中时加分，明显错配时降权；候选证据保留 `building_types` 元数据。
- 版本日期适用：规范问答和 IFC 合规审查支持 `applicable_date`，检索候选会标注“施行日期晚于项目日期”并写入生成上下文；版本对比页增加项目日期输入，逐版本显示是否适用。

评测方法：

- 批量解析：选择 2 个 IFC，模型列表应出现 2 条记录，解析进度可见，切换后模型摘要、项目条件和问答互不串用。
- 报告：有模型问答或审查问答后，可导出 Markdown 和 JSON；JSON 必须包含报告编号、模型快照、结论汇总、逐条问答和引用来源。
- 建筑类型：检索“商业综合体疏散楼梯”候选应包含 `building-type: 命中建筑类型` 提示；检索“住宅户门”时汽车库条文应被降权。
- 版本日期：版本对比选择 2024-01-01 时，GB 55038-2025 应标记为“晚于项目日期”；QA 返回的 GB 55038-2025 证据应带 `version_applicable=false`。

验证结果：

- 后端单元测试 56/56 通过。
- 前端生产构建通过，Sites 测试 4/4 通过。
- 浏览器实测批量选择 2 个 IFC 后模型列表出现 2 条记录，解析完成后自动切换到最后一个模型，进度提示消失。
- 版本对比接口以 2024-01-01 查询住宅户门：GB 55037-2022 标记适用，GB 55038-2025 标记不适用。
- QA 接口以 2024-01-01 查询住宅户门：GB 55038-2025 证据返回 `version_applicable=false`，并显示建筑类型命中提示。
- 版本对比评测 7/7 通过。

剩余问题：

- 批量解析当前为前端顺序队列，暂未支持服务端任务状态、失败重试和并发限制；后续企业化需要迁移到后端队列。
- 建筑类型过滤基于文本启发式，后续可升级为入库时结构化标签，避免依赖条文开头措辞。
- 版本日期适用目前只做标注和提示，尚未在结论层强制排除晚于项目日期的规范，需要后续结合审查日期口径做结论级门控。

## 迭代 46：P2 四项能力落地

目标：完成空间图谱、可选 Qdrant 向量后端、可选访问令牌和运行观测四项 P2 能力，且默认不破坏现有 FAISS 与本地运行。

修改要点：

- 空间图谱：解析字段页新增数据驱动 SVG 关系图谱，按楼层展示空间、门、窗、楼梯的包含关系，不预设建筑类型。
- Qdrant 可选后端：新增 `qdrant_retriever.py`，配置 `QDRANT_URL` 且安装 qdrant-client 后可用；未配置或不可用时继续使用 FAISS，系统状态页显示当前后端。
- 访问控制：后端支持可选 `APP_ACCESS_TOKEN`，启用后除健康检查外需要 `Authorization: Bearer`；系统状态页可保存本机令牌。
- 完整观测：新增 `observability.py`，记录 HTTP 请求数、失败数、耗时、端到端接口分布，以及 DeepSeek 调用次数、失败数、耗时和 Token；新增 `/api/status/metrics`，系统状态页展示。

评测方法：

- 图谱：进入解析字段页应出现关系图谱 SVG，楼层节点数量和模型楼层一致，未归属对象仍由关系树展示。
- Qdrant：未配置 `QDRANT_URL` 时，系统状态应显示 `faiss`，检索行为不变；配置后显示 `qdrant`。
- 访问控制：未设置令牌时访问控制显示“未启用”；设置 `APP_ACCESS_TOKEN` 后，无令牌请求返回 401，带正确 Bearer 返回 200。
- 观测：发起规范问答后，`/api/status/metrics` 的 HTTP 请求数和 LLM 调用数增加，Token 数大于 0；系统状态页展示请求观测、LLM 观测、向量后端和访问控制状态。

验证结果：

- 后端单元测试 58/58 通过。
- 前端生产构建通过。
- 浏览器实测解析字段页出现关系图谱 SVG，楼层节点数为 6。
- 系统状态页出现 8 张状态卡片，包含请求观测、LLM 观测、向量后端和访问控制；令牌面板可保存本机令牌。
- `/api/status/metrics` 返回 `access_control=false`、`vector_backend=faiss`，未配置 Qdrant 时行为不变。

剩余问题：

- Qdrant 当前为可选适配层，尚未提供自动建集合/迁移脚本；真正切换需要先安装 qdrant-client 并配置外部服务。
- 访问控制只支持单一 Bearer 令牌，暂不支持用户体系、角色、会话过期和限流。
- 观测为进程内存统计，重启后清零；长期运营需要落库或接入 Prometheus。
